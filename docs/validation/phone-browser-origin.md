# 离线浏览器传感器来源验证

验证日期：2026-09-19。环境：macOS、Chrome 152、本机启动的局域网 HTTP / HTTPS 手机网关。页面为 `/sensor-check.html`，不依赖配对服务、外部脚本或互联网。

## 桌面验证结果

| 场景 | 实际操作 | 结果 |
| --- | --- | --- |
| 局域网 HTTP | 通过电脑的局域网 IP 打开检测页 | `window.isSecureContext === false`；`navigator.mediaDevices`、`getUserMedia` 与 `DeviceMotionEvent` 均未暴露。 |
| 本地 HTTPS，未信任证书 | 使用本地签发证书直接打开检测页 | Chrome 首先显示 `ERR_CERT_AUTHORITY_INVALID` 证书提示。 |
| 本地 HTTPS，浏览器中继续 | 在真实证书提示页面点击 Advanced → Proceed；没有安装系统 CA | 检测页成功打开；`window.isSecureContext === true`，媒体采集和运动接口均暴露。 |
| 同一 HTTPS 路径，模拟媒体验证 | 单独 Chrome 会话仅加入 `--use-fake-device-for-media-stream` 与 `--use-fake-ui-for-media-stream`；仍通过真实证书提示页面手动继续，然后分别点击检测页麦克风和摄像头按钮 | 两项记录均为 `permission: granted`、`receivedData: true`、`status: working`。模拟音频样本与模拟视频帧通过页面的实际数据检测。 |

上述浏览器会话保留 TLS 检查，设置为 `ignoreHTTPSErrors: false`；没有使用忽略证书错误的启动参数，也没有将 CA 安装到系统信任库。媒体验证使用的两个模拟媒体参数仅用于提供测试设备和自动同意媒体权限，不取消 TLS 检查。

## 结论与边界

该桌面 Chrome 环境证明：本地 HTTPS 证书未受系统信任时，经浏览器提供的继续访问流程，仍可以获得安全上下文并实际运行媒体采集接口。因此不能把“必须先安装根证书”描述成所有浏览器的共同要求。默认连接入口可以直接指向电脑的局域网 HTTPS 页面，并把安装证书保留为可选兼容方案。

这些结果不证明所有手机都能扫码即用，也不证明所有浏览器会提供继续访问选项或在继续后开放传感器。上述桌面测试未使用 Android 或 iPhone 实机；其媒体数据完全来自 Chrome 模拟设备，未采集真实音频或图像。用户随后反馈的手机权限结果另记如下，不能与桌面模拟数据合并为硬件采集通过。运动接口暴露只属于能力检测，不能标记为运动采集成功。

手机验收仍需在实际手机浏览器中，分别打开网关提供的 HTTP 和 HTTPS 检测地址，主动点击各项测试按钮，记录是否出现证书提示、是否能继续、是否收到真实数据。页面可复制或下载本地脱敏 JSON，不会将结果上传服务器。若手机浏览器阻止访问或采集，应如实报告兼容性边界，不能声称网页 JavaScript 能绕过该限制。

## 用户反馈：手机权限申请

用户已报告 Android Chrome 与 iPhone Safari 两端均可以申请权限。此项记录来源为用户反馈，范围仅限手机浏览器能够进入权限申请流程；尚未取得可复核的逐项真实传感器数据及完整实验接入记录。不能据此标记手机麦克风、摄像头、运动数据、保存/回放或异常停机的全链路验收通过，也不推断未报告的机型、浏览器版本或证书提示操作。

## 产品集成：已建立直连被路径检查误拒

集成中观察到 WebRTC 已建立直连，但选中候选对为本地 `prflx`、远端 `host`，原先仅接受双方均为 `host` 的检查将其误拒。路径检查已修正：选中候选对必须成功，且本地和远端候选类型分别只能为 `host` 或 `prflx`；`srflx`、`relay` 和未知类型仍不接受。

`prflx` 是 peer-reflexive 候选，与 TURN 中继候选 `relay` 不同；类型定义见 [W3C RTCIceCandidateType](https://www.w3.org/TR/webrtc/#dom-rtcicecandidatetype)。不配置 STUN/TURN 服务器，信令及 SDP 仍只交换 `host` 候选；允许连接检查过程中产生的 `prflx` 选中路径，不等于放宽信令候选规则或启用云端中继。候选类型本身不能证明双方属于同一个物理 Wi-Fi。

此记录说明误拒原因及修复范围，不代表修复后 Android/iPhone 的真实硬件采集全链路已验收。实际数据进入实验、保存以及断线清理仍按原验收范围记录，不由权限申请成功或 WebRTC 连通推断通过。

## 产品集成：浮点音频峰值导致采集停止

在独立产品联调会话中，Chrome 模拟麦克风经过实际 AudioWorklet、WebRTC 数据通道与本机服务，产生了 96000 Hz、每批 1920 样本的音频。失败批次最小值约 -0.1162，最大值约 1.1298；原服务强制要求所有样本位于 [-1,1]，因而将合法浮点峰值拒绝，并触发手机输入断开。

[Web Audio 的 AudioBuffer 定义](https://www.w3.org/TR/webaudio-1.0/#AudioBuffer) 将此范围定义为名义范围，浮点样本并不受其限制。修正为保留有限 Float32 范围内的原始值，不做截幅或额外增益；采样率、批次长度和传输约束保持验证。这是软件采集链路问题，不代表手机硬件音量或声压标定结果。

产品联调使用模拟媒体，并为便于调试设置 `ignoreHTTPSErrors: true`。它只验证采集软件链路，不作为绕过证书提示或 Android/iPhone 浏览器兼容性的证据；前述证书行为验证属于独立保留 TLS 检查的会话。

## 单页设置与采集流程

桌面工作台使用 `http://127.0.0.1:8765`，手机页使用本机 LAN HTTPS；两个独立 Chrome 上下文通过实际配对、WebRTC 数据通道与服务接口联调。测试数据使用独立临时目录，不混入用户实验。

- 侧栏为实验库、当前实验、数据与回放、设置。设置同页展示手机、电脑音视频和外部设备，无二级配置页面；1280px 与 900px 窗口均无横向溢出。
- 从实验库选择手机入门实验会先定位设置页，绑定后再进入测量。已有连接可复用，手机停止采集后仍保留配对。
- Chrome 模拟麦克风的 96000 Hz PCM 通过实际传输进入实验；开始、暂停、继续、本机保存及 CSV ZIP 下载均完成，导出文件含采样数据、采样率与会话元数据。
- Chrome 模拟摄像头通过 JPEG 传输进入手机相机颜色实验，服务产生色相、饱和度和相对亮度数据。标准 sRGB ICC 不再因仅存在 ICC 字段被拒绝；未知颜色配置仍拒绝，不冒充已完成颜色转换。
- 使用 `new DeviceMotionEvent(...)` 构造的合成运动事件通过实际通道进入手机运动实验，x/y/z 为输入的 1/2/9.8。修复了展开 Web IDL 向量对象时遗漏原型 getter 坐标的问题。该项验证事件处理和传输，不代表真实加速度计或陀螺仪验收。

这些检查针对当前改动，不替代 Windows 可执行文件启动与 Android/iPhone 硬件验收。Windows x64 交叉构建可以检查包结构；当前开发机未运行 Windows 程序。
